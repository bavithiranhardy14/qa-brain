## Coverage Summary

All four acceptance criteria are covered by at least one functional test. The story covers the core happy path (request reset → receive email → set new password → login), the password history constraint (last 3), and the lockout-reset linkage. Negative and boundary tests cover token expiry, password reuse, and invalid input handling.

---

## Missing Areas

- **Unregistered email behaviour not defined**: AC-1 covers registered email only. No AC defines the response for an unknown email. System should return a generic message to prevent email enumeration — this is a **blocking security gap**.
- **No AC for multiple concurrent reset links**: If a customer requests two links, only the latest should be valid. Assumed in Notes but not an explicit AC.
- **No AC for rate limiting**: Nothing prevents mass reset requests. A rate-limit or CAPTCHA rule is absent.
- **No AC for success notification**: No mention of notifying the customer that their password was changed.
- **No AC for new password complexity**: AC-3 covers reuse but doesn't explicitly require the new password to meet the standard complexity policy.

## Recommendations

1. Add AC: "If the email is not registered, return a generic message: 'If this email is registered, a reset link has been sent.' Do not reveal whether the email exists."
2. Clarify AC-4: "Account unlock is triggered when the customer successfully saves a new password."
3. Add AC: "The new password must meet the standard password complexity policy (min 8 chars, 1 uppercase, 1 lowercase, 1 digit, 1 special character)."
4. Add AC: "Only the most recently issued reset link is valid; earlier links are invalidated upon a new request."
5. Consider adding: "Max 3 password reset requests per hour per email address."
